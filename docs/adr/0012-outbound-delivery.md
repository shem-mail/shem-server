# ADR 0012: Outbound Queue, Remote Delivery, and DKIM Signing

Status: accepted for Phase 4. DANE and TLS reporting are not implemented; see the residual risk below.

## Decision

### Queue (`shem-outbound`, `OutboundQueue`)

- **Location:** `queue/` in the data directory, owner-only, separate from `mailboxes/`. Each item is two files:
  - `<id>.eml`: the exact bytes to transmit, already DKIM-signed.
  - `<id>.state`: a versioned binary record (`SHOQ` v1) holding the envelope sender, per-recipient status and last reply summary, created and expiry times, the next attempt and attempt count, and whether the sender was notified.
- **Plaintext by design:** this is the whitepaper's single deliberate exception to encryption at rest. The content is readable on disk and in backups.
- **Never stored in the queue:** passwords, mailbox keys, or unlock tokens. Delivery needs no user session.
- **Durability:**
  - The message file is synced and published first, then the state file. An item exists once its state file exists.
  - At startup, orphan message files and temporary files are deleted, and a corrupt state record fails startup (fail closed).
  - Transitions replace the state file atomically.
  - Removal deletes the state first, so a crash cannot resurrect a removed item.
- **Admission:** bounded by `outbound.maxItems` (10 000) and `outbound.maxBytes` (2 GiB). A full queue gets `452 4.3.1`.
- **Lifetime:** `outbound.lifetime` (5 days).
- **Retention:** finished items are deleted promptly. There is no per-message delivery history, only aggregate counters.

### Submission routing

- **Signing:** submission DKIM-signs the message whenever the From domain has a selector and key.
- **Remote recipients:** queued before any local copy is written, so a full queue refuses the whole transaction with nothing committed.
- **Local recipients:** get the same signed bytes through encrypted delivery. An all-local message never touches the queue.
- **Duplicates:** if a local delivery then fails temporarily, the client's retry can duplicate the remote copy, the same ambiguity as inbound (ADR 0009).

### DKIM (`DkimSigning`)

- **Algorithm:** rsa-sha256, relaxed/relaxed, over From, To, Cc, Reply-To, Subject, Date, Message-ID, In-Reply-To, References and the MIME headers.
- **Streaming:** signing uses jDKIM's streaming API (bounded header read, streamed body hash), not its whole-message parser.
- **Keys:**
  - PKCS#8 PEM files in `dkim/<selector>._domainkey.<domain>.key`, owner-only.
  - Generated by `shem dev dkim-key DOMAIN SELECTOR` until the admin API exists (step 14). The command prints the TXT record to publish.
  - Existing keys are never overwritten, so rotation means a new selector and in-flight signatures stay verifiable.
  - DKIM keys are server-wide secrets that no mailbox password protects. A leaked key or backup allows signing for the domain but never unlocks a mailbox.
  - A signing failure is a temporary rejection; mail is never queued unsigned when a key exists.
- **Not yet:** Ed25519 dual signing, which needs its own interoperability testing.

### Delivery (`OutboundDelivery`)

- **Scheduling:** a ticker every 30 s starts due items on virtual threads, with at most `outbound.maxConcurrent` at once.
- **Routing (RFC 5321 section 5.1):**
  - MX hosts are ordered by preference (at most 10).
  - With no MX, the domain itself is used (implicit MX).
  - RFC 7505 null MX is a permanent failure.
  - A temporary DNS failure is retried.
- **Per recipient:**
  - `2xx` is delivered.
  - `5xx` is a final failure.
  - Anything else, including connection loss, is retried on the schedule (5 min, 30 min, 1 h, 2 h, then every 4 h) until expiry.
  - Recipients of one domain share a transaction (at most 100).
  - A failure after the final dot may resend the message on retry, an unavoidable ambiguity.
- **Retained diagnostics:** only the reply code and enhanced status (for example `550 5.1.1`), never transcripts.
- **TLS:**
  - Without an enforced MTA-STS policy, STARTTLS is used when offered, opportunistically and without peer authentication (RFC 7435). A failed handshake falls back to plaintext for that host.
  - With an `enforce` policy (RFC 8461):
    - Only MX hosts matching the policy are used.
    - STARTTLS is required, and the certificate must validate (JDK trust store) and match the MX name.
    - Otherwise the attempt is deferred, never downgraded.
  - Policies are discovered through `_mta-sts` TXT and fetched over validated HTTPS: no redirects, no proxy, 64 KiB, timeout.
  - Before fetching, every address of `mta-sts.<domain>` must be public unicast (SSRF guard). The HTTP client resolves the name again, a narrow residual race.
  - Policies are cached in memory, bounded, with `max_age` capped at one year. A failed or blocked refresh keeps an unexpired cached policy, so blocking discovery cannot downgrade a domain.
- **DSNs:**
  - When nothing is pending and recipients failed, one RFC 3464 report goes to the local sender through encrypted delivery.
  - The report has a null reverse path and includes only the original headers (at most 64 KiB), never the body.
  - The queue item id serves as the delivery id, so a lost state update cannot produce a second DSN.
  - Items with a null sender (DSNs themselves) never bounce.

## Residual risk

- **DANE is not implemented.** It needs a DNSSEC-validating resolver. Without validated TLSA evidence there is no DANE assurance, and none is claimed.
- **No TLS reporting (TLSRPT)** and no "delayed" DSNs.
- **Opportunistic TLS** protects against passive observers only.
- **Metadata exposure:** recipient domains appear in DNS queries and in the queue. Queue contents are readable by anyone with access to the service account or backups.
- **No Process isolation yet:** the queue runs in the same process as the other roles (ADR 0007 is still open).
- **No `SIZE` or `8BITMIME` negotiation:** messages are sent as submitted.

## Evidence

- **`OutboundQueueTest`:**
  - restart persistence of state transitions
  - due scheduling
  - removal leaving no files
  - crash leftovers removed
  - a corrupt state record failing closed
  - owner-only directory
  - item and byte bounds
  - state record round trip
- **`OutboundDeliveryTest`**, against a scriptable SMTP peer:
  - opportunistic TLS delivery of exact, dot-stuffed bytes with no mailbox keys involved
  - a `5xx` recipient producing one DSN to the sender's mailbox
  - `4xx` retried on schedule after a queue restart
  - MX fallback past a dead host, null MX, and implicit MX
  - expiry producing a DSN
  - MTA-STS enforce deferring without STARTTLS and with an untrusted certificate, then delivering with a valid one
  - MTA-STS excluding unlisted MX hosts
- **`MtaStsAndDkimTest`:**
  - policy parsing and wildcard matching
  - a cached policy surviving blocked discovery and refreshing on a new id and after `max_age`
  - the SSRF address filter
  - generated keys being owner-only and never overwritten
  - signed bytes verifying with jDKIM and tampering failing
  - domains without keys left unsigned
- **`SubmissionIT`:**
  - queued bytes and the local copy both verify against the published key
  - all-local mail never queued
  - a full queue giving `452` with nothing committed locally
- **Manual `serve` run:** `dev dkim-key`, then submission over STARTTLS to a remote address. The queued message was signed, and delivery was deferred because the sandbox has no outbound SMTP.
