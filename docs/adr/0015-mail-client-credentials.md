# ADR 0015: Mail Clients Use Only System-Generated App Passwords

Status: accepted. Decision by the project owner: users must let the system generate their IMAP/SMTP password, and the main password cannot be used by mail clients.

## Context

IMAP and SMTP submission cannot ask for a second factor. With mandatory MFA on the HTTP API ([ADR 0014](0014-mfa.md)), a stolen main password would still have opened the mailbox over IMAP, bypassing the second factor entirely.

## Decision

### Login paths

- IMAP (`ImapAuthentication`) and submission (`SubmissionAuth`) authenticate through `SessionService.authenticateMailClient`, which only tries app-password slots.
- The main password, bootstrap passwords and recovery codes never work for mail clients.
- A credential that is not in app-password format still pays the same KDF cost and limiter accounting, and gets the same generic failure as a wrong password:
  - IMAP: `NO` / `AuthenticationFailed`
  - SMTP: `535 5.7.8`

  So the response does not reveal which kind of password was tried.

### App passwords

- **Always generated by the server:** `KeyLifecycle.createAppPassword` takes only a label. There is no way to choose one.
- **Format:** `ssss-xxxx-xxxx-xxxx-xxxx-xxxx-xxxx`, base32.
  - The first group is a public selector that picks the slot file without trying every slot.
  - The six random groups hold 24 characters × 5 bits = 120 bits from `SecureRandom`.
  - A main password may not have this shape (`Credentials.isAcceptablePassword`), so the two kinds can never be confused.
- **Lifecycle:**
  - Created through `POST /api/v1/me/app-passwords`, which requires a full session (password plus second factor) and a recent login.
  - Shown once, never stored in plaintext. Each app password has its own key slot, protected with Argon2id like every slot.
  - Deleting one ends its live IMAP and SMTP sessions.
  - App passwords carry `MAIL_ACCESS` and `SUBMIT` but not `KEY_ADMINISTRATION`, and they are refused for API login (`authenticatePrimary`). A leaked app password reads and sends mail but can't change credentials or factors, and can't reach the API.
- **Rotation:** key rotation removes all app passwords, as before; users create new ones.

### Development

`shem dev app-password ADDRESS LABEL` (development mode only) creates one from the command line with the main password. It bypasses the web second factor, like the other gated dev commands, and is refused in production mode.

## Consequences

- Users set up mail clients with a generated app password per device. Losing a device means deleting that one app password, not changing the main password.
- **Remaining exposure:** a stolen app password gives mail access until it is deleted. That is the inherent limit of protocols without a second factor, now confined to one device's credential.

## Evidence

- `MailboxVerticalSliceTest`: `authenticateMailClient` refuses the primary password and accepts an app password; `authenticatePrimary` refuses app passwords.
- `ImapClientIT`: the primary password is refused by a real IMAP client (Jakarta Mail). All other IMAP tests run with an app password.
- `SubmissionIT`: the primary password gets the exact same `535` as a wrong password. All submission tests, including Jakarta Mail over STARTTLS, use an app password.
- `DevBootstrapCommandTest`: the dev command prints a correctly formatted app password.
