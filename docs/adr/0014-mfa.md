# ADR 0014: Mandatory Second Factor for the HTTP API (TOTP and WebAuthn)

Status: accepted. Decision by the project owner: support both TOTP and WebAuthn, and require every user to register at least one factor.

## Decision

### Factors

- **TOTP** (RFC 6238): HMAC-SHA1, 30-second steps, six digits, 160-bit secret, one step of drift either side. It is computed in `shem-crypto` (`Totp`).
  - The accepted time step is stored, so a code, or any earlier one, can never be reused.
  - Enrollment returns the base32 secret and an `otpauth://` URI once, and is confirmed with a valid code.
- **WebAuthn**, verified by webauthn4j 0.29.7 and never hand-rolled:
  - The relying party ID is the host of `http.origin`, and the origin must match exactly.
  - Accepted algorithms: ES256, EdDSA, RS256.
  - Attestation `none` is accepted, because the server trusts the authenticator a logged-in user registers, not a vendor chain.
  - User presence is required. User verification is preferred but not required, since the password has already been checked.
  - The stored signature counter must increase. A counter that does not increase, other than an authenticator that always reports zero, is refused as a possible clone.
  - Duplicate registrations are refused.

### Storage

Factors live inside the sealed keyring (format 2), encrypted under the mailbox master key, so:

- Nobody without the password can read a TOTP secret or the list of security keys, the server operator included.
- Factors are rewritten atomically with every password change, rotation and enrollment; a crash cannot leave them sealed under the wrong key.
- Format-1 keyrings (no factors) still open. That is proven by a committed fixture, and they are rewritten as format 2 only on the next legitimate key change. The format version is bound into the associated data, so a downgrade fails to open.

### Login flow

- **Password with factors:** `POST /auth/login` with a correct password for an account that has factors returns `{mfaRequired, challenge, methods}` and no session.
  - The pending login holds the mailbox lease for at most 5 minutes and 5 attempts, then the lease is closed.
  - The login completes with `POST /auth/mfa/verify` using `totp`, or `webauthn` after `POST /auth/mfa/webauthn-options`.
  - Ten factor failures for one account within 15 minutes block further logins for that account (`429`) until the window passes. This is protection against online guessing.
- **Password without factors:** the session is restricted (`mfaEnrollmentRequired: true`).
  - It may only use `/me`, logout, and the factor endpoints. Every other route returns `403`.
  - Registering the first factor completes the session.
- **Bootstrap credentials:** these sessions can only enroll a password (unchanged). The next login then requires factor enrollment.
- **Recovery code login:** skips the second factor, because the recovery code is itself a user-held high-entropy secret meant for the lost-device case. The session can only change the password and manage factors, and only a recovery session may remove the last factor.

### Factor management

| Endpoint | Purpose |
| --- | --- |
| `GET /me/mfa` | List factors |
| `POST /me/mfa/totp`, `/me/mfa/totp/confirm` | Enroll TOTP |
| `POST /me/mfa/webauthn/options`, `/me/mfa/webauthn` | Enroll a security key |
| `DELETE /me/mfa/{id}` | Remove a factor; refused for the last factor, except from a recovery session |

Enrolling or removing a factor needs a recent login (step-up, ADR 0013).

### Removed

`http.allowWithoutMfa`, the temporary production opt-out from ADR 0013, is gone, and setting it fails startup as an unknown key.

## Open question (raised, not decided)

MFA protects the HTTP API, including account and key management. IMAP and submission cannot do a second factor, and they still accept the primary password. A stolen password therefore still reads mail over IMAP, but cannot change credentials or factors. The usual answer is to accept only app passwords for IMAP and SMTP once a factor exists. That changes client setup, so it needs the owner's decision.

## Residual risk

- **TOTP is phishable;** WebAuthn is not.
- **Unwipeable copies** of the TOTP secret exist briefly in the JCE `Mac` and in the one-time enrollment response.
- **Restart behaviour:** pending logins and factor-failure counters are in memory and reset on restart. The KDF limiter and the per-IP limiter still apply.

## Evidence

- `MfaTest` (crypto):
  - RFC 6238 SHA-1 vectors and base32 encoding
  - the drift window and replay rejection
  - factors sealed in the keyring and surviving slot changes and rotation
  - the format-1 fixture opening unchanged, and a format-byte downgrade failing authentication
- `MailboxVerticalSliceTest`: factors persist across key rotation along with their replay counter; the last factor is protected.
- `HttpMfaIT`:
  - restricted sessions until TOTP enrollment, a wrong confirmation code refused, and the enrollment code not replayable at login
  - single-use challenges, attempt exhaustion, pending expiry releasing the mailbox, and the account lock and its expiry
  - WebAuthn registration (a wrong challenge is refused) and login with a test authenticator that builds real CBOR, client data and ECDSA assertions
  - replayed assertions refused, the last-factor rule, and removing a key after adding TOTP
- `HttpApiIT`: all earlier API behaviour, now through the second-factor step.
